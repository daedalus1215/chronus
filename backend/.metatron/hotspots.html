Chronus Frontend Backend Hotspots

Every file placed by how often it has changed against how much of the codebase depends on it. The top-right corner is where refactoring pays for itself — code that churns constantly and that everything else leans on. Quiet code, however ugly, costs you nothing. Files with no test carry a dashed ring, so the corner doubles as a test backlog: a ringed dot up there is the file to test first.

Reading it

Horizontal is how many files import this one — change it and they all feel it. Vertical is how many commits have touched it. Dot size is total lines added and removed; colour runs from calm to hot on the product of the two axes.

Neither axis is bad on its own. A widely-depended-on file that never changes is a stable foundation, exactly what you want. A file that churns constantly but nothing imports is cheap to get wrong. It is the corner where both are true that earns attention.

What this does not know

Commits are a proxy for churn, not a measure of it: a file touched once by a huge refactor scores lower than one nudged twenty times. Renames are followed only where git reports them in the same commit. And a high score is not a verdict — a core repository is supposed to be depended on, and may be changing often because the product is moving. The chart says where to look, not what to do.
